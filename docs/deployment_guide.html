🔒 HTTP vs HTTPS & SSL Decrypted

At their core, HTTP and HTTPS are languages used to send data back and forth between a browser and a server. The critical difference is **safety**.

HTTP (Port 80)

Data is sent in clear text. Anyone intercepting the packets (like a hacker on public Wi-Fi) can see passwords, tokens, and stream contents.

HTTPS (Port 443)

Data is fully encrypted using SSL/TLS. Even if intercepted, it looks like random gibberish. Web Browsers require this context for sensitive features.

What is SSL/TLS and why did Selkies complain?

SSL (Secure Sockets Layer) is the protocol that performs the encryption. To enable it, a trusted authority (like Let's Encrypt) issues a digital "Certificate" verifying your server's identity.

Why Selkies failed initially: Modern browsers block critical features (like clipboard capture, pointer lock, and audio streaming) unless they detect a Secure Context (HTTPS). Serving the sandbox over `http://` caused the browser's JavaScript to throw an error and refuse to connect.

🔀 What is a Reverse Proxy & Caddy?

When you run SecureBuddy, it runs on port `3000`. We don't want to expose port `3000` directly because it doesn't have SSL capabilities built into it natively. Instead, we use a **Reverse Proxy**.

A reverse proxy acts like a gatekeeper receptionist sitting at the entrance (port 80/443). It receives HTTPS requests, handles the encryption handshake, and then quietly forwards the traffic internally to your Node.js application.

Understanding the Caddyfile Configuration

In step 3, we wrote a short block of code into `/etc/caddy/Caddyfile`:

securebuddy.duckdns.org {
    reverse_proxy localhost:3000
}

Here is what this means line by line:

  • securebuddy.duckdns.org: Tells Caddy to listen for requests specifically meant for this domain name. It automatically contacts Let's Encrypt to download a free SSL certificate for this domain.
  • reverse_proxy localhost:3000: Instructs Caddy to take any requests hitting that domain on port 80/443, strip/handle the SSL encryption, and pass the clean traffic to your Node app running locally on port `3000`.

🛡️ The Double-Lock Firewall

For security, cloud networks use a **two-layered security design** to lock down ports. A packet coming from the internet must pass through both locks to reach your app.

Lock 1: Oracle Ingress Rules
External Network Shield

This is a firewall hosted by Oracle Cloud outside your server. If you don't open ports 80/443 here, the packet is blocked before it even touches your virtual machine.

Lock 2: Local VM iptables
Internal Server Gatekeeper

This is a software firewall running inside your Ubuntu VM OS. Ubuntu drops all traffic unless an explicit rule allows it.

Understanding the `iptables` Command

To open ports inside your Ubuntu OS, we ran these commands:

sudo iptables -I INPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -I INPUT -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save
  • -I INPUT: Inserts the rule at the very top of the incoming packet rules. This is crucial because Oracle VM images have a drop rule at the bottom; inserting at the top ensures the permit rule is evaluated first.
  • -p tcp --dport 80: Matches incoming TCP traffic destined for port 80 (HTTP).
  • -j ACCEPT: Accepts/allows the packet.
  • netfilter-persistent save: Saves the rules to disk so they are not wiped out when the VM reboots.
